# Capacity baseline — 29 September 2026

This is development evidence for the 0.9.0 release tracker [#99](https://github.com/fermi-ad/redis-pvxs-ioc/issues/99), measured on adlinux3. It is **not final 0.9.0 qualification**. The [raw JSON](capacity-2026-09-29.json) retains all measurements, revisions and environment details.

The demonstrated lossless points were a 10,000 Hz scalar, a 2,500 Hz 4096-element UInt32 array (39.06 MiB/s of application payload), and a 1,000 Hz scalar delivered to 16 independent clients. Each scalar/array/fan-out trial lasted approximately ten seconds. These points do not establish maximum throughput or long-term memory behavior.

## Measurements

“Missed” counts sequence values not observed by a monitor, summed across clients. “Repeated” counts repeated observed sequence values. PVA monitors represent changing state and can coalesce intermediate updates; this report does not assume every missed value originated in a particular queue.

| UInt32 scalar | 100 | 1,000 | 0 / 0 | 0.361 / 0.571 / 0.630 | 1/16 | 19.50 |
| UInt32 scalar | 1,000 | 10,000 | 0 / 0 | 0.160 / 0.367 / 0.459 | 1/16 | 19.70 |
| UInt32 scalar | 10,000 | 100,000 | 0 / 0 | 0.122 / 0.150 / 0.166 | 1/16 | 19.24 |

At 5,000 Hz with 16 clients, 224 of 800,000 expected intermediate observations were absent (0.028%) and 10 repeated values were observed. Every client's final value converged. This load is **not a demonstrated lossless operating point**. PVXS client/server squash counters remained zero, so those counters alone do not locate the missing intermediate values.

The separate imaging transfer passed **600/600 exact 1920×1080 Mono8 frames at 10 fps**, checking 1,244,160,000 pixels, frame order and acquisition timestamps. It had zero unexplained gaps/duplicates, p50/p95/p99 latency of 7.081/8.511/9.082 ms and IOC peak RSS of 40.66 MiB. [Imaging evidence](https://github.com/fermi-ad/redis-pvxs-ioc/issues/99#issuecomment-5900188886) includes the report and an ancillary postprocessing error disclosure.

## Method and limits

- Runtime: IOC `47626c7d8a31d42defa3b8fce5dbe72f7e737896`, embedded version `0.8.2`; immutable local image ID `sha256:8fda7b8cf67e494f598f3ed4639b562bac2d59b420f4efa71ab65ea51e4b330b`. This is a CI development image, not a published stable release.
- Dependencies: adapter `0bb9c35e7480e5d01afd58a5ed5ce27f3191f226`, PVXS `8e00eaecdee5ce8a474704e70d820e6f92693fa1`. The pending adapter recovery/status changes, including their XINFO traffic, were not present.
- Each case used a fresh private Redis and IOC on an internal Docker bridge with no published host ports. UID 10001, read-only IOC root, dropped capabilities; IOC/Redis memory limits 256 MiB each, client 512 MiB. The five existing host services were unchanged; test containers and networks were removed.
- Fan-out used 16 independent PVA client contexts subscribing to one canonical PV. Clients were established sequentially before timing; total connection setup was 0.185–0.189 seconds. A simultaneous connection burst twice exceeded the fixture's five-second bound; [#122](https://github.com/fermi-ad/redis-pvxs-ioc/issues/122) remains open. Sequential establishment does not resolve it.
- Each Redis stream retained exactly 16 entries; each PVA monitor requested a 16-entry pipelined queue. Every delivered array element was checked. Latency runs from immediately before Redis XADD to receipt by the PVA callback, using the same process's monotonic clock. Imaging used acquisition wall-clock timestamps on the same host.
- The UInt32 measurement client also validates payloads and produces the stream; its overhead is included. Source revisions are recorded per case because the fan-out setup was corrected after the scalar/array runs. No automatic workload retry hides a failed case.
- RSS is process high-water RSS, not total cgroup memory/file cache. Across scalar/array/fan-out cases, the IOC stayed below 20 MiB. Write queue peak reservations were zero for these read-only workloads; alarm reservations peaked at approximately 1 MiB and pending queues drained to zero. These are separate from client monitor queues. The current adapter API does not expose its reader callback backlog.

## Reproduce

Build `stream_capacity` with the normal CMake build. The native short acceptance fixture runs three private scalar/array/16-client cases:

```sh
cmake --build build --target stream_capacity redis-pvxs-ioc
ctest --test-dir build -R '^stream_capacity_e2e$' --output-on-failure
```

For a longer run, use a private IOC whose read-only UInt32 PV reads key `data` under a fresh Redis base key; use `shape: array` for more than one element. With that IOC and Redis already running:

```sh
./build/stream_capacity --redis-host REDIS_IP --redis-port 6379 \
  --base-key UNIQUE_PRIVATE_KEY --pv CAP:value --pva-address IOC_IP:5076 \
  --elements 4096 --clients 1 --rate 2500 --samples 25000 \
  --output NEW_REPORT.json
```

Use `--elements 1 --clients 16 --rate 1000 --samples 10000` for fan-out. The tool refuses an existing stream/report, checks initial readiness and final convergence, and reports missed/repeated values rather than silently declaring lossless delivery.
